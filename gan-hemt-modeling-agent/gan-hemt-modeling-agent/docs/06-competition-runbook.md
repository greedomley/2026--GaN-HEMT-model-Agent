# 24 小时竞赛运行计划

## 1. 运行原则

- 两套器件使用独立会话、状态、日志和模型卡版本链。
- 先确保两套器件都有可提交基线，再追求高精度。
- 后半程优先改善评分代理更低、风险更高的器件。
- 最后两小时只做验证、冻结和提交，不做高风险算法修改。

## 2. 时间安排

| 时间窗 | 目标 | 关键产物 |
|---|---|---|
| 0–1 小时 | 启动、鉴权、健康检查、两器件建会话 | preflight 报告、会话记录 |
| 1–3 小时 | 数据清点与审计，生成初始计划 | 两份数据 QA、两份提参计划 |
| 3–6 小时 | 两器件各自产出首份可提交基线 | 基线模型卡与检查点 |
| 6–13 小时 | 分组完成 DC、C-V、S 参数、温度、Pulse 等提取 | 参数组最佳版本链 |
| 13–17 小时 | 全局优化、物理 QA 和 retune | 最佳已验证模型卡 |
| 17–20 小时 | 对比两器件，集中改善较弱器件 | 双器件评分代理报告 |
| 20–22 小时 | 完整验证、恢复性检查、冻结候选 | 最终冻结候选 |
| 22–23 小时 | 生成并校验 2 卡、2 日志、1 总结 | 完整提交包 |
| 23–24 小时 | 上传、复核和故障缓冲 | 提交确认与校验记录 |

## 3. 时间门禁

- 第 3 小时：必须完成两套器件的数据审计。
- 第 6 小时：必须各有一份可提交模型卡。
- 第 17 小时：必须停止无边界探索，转入双器件比较。
- 第 20 小时：禁止引入未经回归的策略。
- 第 22 小时：冻结模型卡，只进行产物校验和必要恢复。

## 4. 故障处理顺序

### MCP 超时或服务错误

先确认调用幂等性，再按预算重试；持续失败时恢复最近检查点，保留当前可提交卡并切换到另一器件。

### 国产大模型限流或不可用

使用已验证的备用国产模型；若仍不可用，执行预定义的确定性降级策略，同时保留已发生的合规调用证据。

### 拟合不收敛或 QA 退化

停止扩大参数搜索，回滚到最近已接受模型卡，缩小参数组或更换已登记策略。

### 进程中断

从持久化图状态和模型卡检查点恢复，不重建已经完成的器件会话，除非官方接口明确要求。

### 时间不足

立即停止低收益 retune，执行最终 QA、Schema 校验、日志封存和提交。

## 5. 提交前人工复核

- 两个器件和两个模型卡没有交叉。
- 文件可打开、可读取、命名符合官方要求。
- 运行日志从启动到冻结连续完整。
- 运行总结中的统计与日志一致。
- 没有 Token、API Key、临时缓存和测试原始数据。
- 上传完成后保留平台确认信息。
