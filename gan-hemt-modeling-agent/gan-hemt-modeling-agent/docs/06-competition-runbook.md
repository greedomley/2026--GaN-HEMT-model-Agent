# 24 小时竞赛运行计划

## 1. 运行原则

- 两套器件使用独立会话、状态、日志和模型卡版本链。
- 先确保两套器件都有可提交基线，再追求高精度。
- 后半程优先改善评分代理更低、风险更高的器件。
- 最后两小时只做验证、冻结和提交，不做高风险算法修改。
- 官方计时开始后，preflight、鉴权和故障等待都计入 24 小时墙钟；赛前 dry-run 才能在窗口外阻断。
- 所有节点传播阶段 deadline，按双器件关键路径而不是调用耗时简单相加来判断是否超预算。
- 包内容结果由确定性校验器判定，平台交付由 `submission_status` 单独记录；严格包、降级有效包、失败安全和上传结果不得混用。

## 2. 时间安排

| 时间窗 | 目标 | 关键产物 |
|---|---|---|
| 0–1 小时 | 启动、鉴权、MCP/国产 LLM endpoint 与结构化输出健康检查、两器件建会话 | preflight 报告、会话记录；健康调用是否计合规以官方 Q&A 为准 |
| 1–3 小时 | 数据清点与审计，由国产 LLM 参与至少一次有意义的计划/风险决策 | 两份数据 QA、两份提参计划与整组合规决策证据 |
| 3–6 小时 | 两器件各自产出首份可提交基线 | 基线模型卡与检查点 |
| 6–13 小时 | 分组完成 DC、C-V、S 参数、温度、Pulse 等提取 | 参数组最佳版本链 |
| 13–17 小时 | 全局优化、物理 QA 和 retune | 最佳已验证模型卡 |
| 17–20 小时 | 对比两器件，集中改善较弱器件 | 双器件评分代理报告 |
| 20–22 小时 | 完整验证、恢复性检查、冻结两份模型卡 | 两份摘要固定的最终模型卡 |
| 22–23 小时 | 组装、验证、判定并冻结 2 卡、2 日志、1 总结 | 不可变有效包或带明确诊断的无效包 |
| 23–24 小时 | 上传、查询回执、复核和故障缓冲 | 官方截止前 `submission_status=CONFIRMED` 的平台确认与校验记录 |

## 3. 时间门禁

- 第 3 小时：必须完成两套器件的数据审计。
- 第 6 小时：必须各有一份可提交模型卡。
- 第 17 小时：必须停止无边界探索，转入双器件比较。
- 第 20 小时：禁止引入未经回归的策略。
- 第 22 小时：冻结模型卡，只进行产物校验和必要恢复。
- 第 23 小时：包内容必须完成验证、判定和冻结，已具备上传条件。
- 第 24 小时前：平台提交必须确认；回执未知时立即进入提交结果对账并保留证据。

## 4. 关键路径与完成门禁

- 记录 `time_to_first_valid_card_by_device`、`time_to_dual_baseline`、`time_to_best_valid_card_by_device`、`time_to_model_cards_frozen`、`time_to_valid_package` 和 `time_to_submission_confirmed`。
- 每个阶段拆分 LLM、MCP 网络/远端计算、拟合、QA、等待、重试和检查点耗时；并行器件按墙钟关键路径计算。
- 第 3/6/17/20/22/23/24 小时门禁都生成机器可读快照，显示保底卡、必做阶段缺口、剩余预算、未知远端操作和未分类失败。
- 延迟优化只有在相同 manifest 的配对 A/B 达到预注册最小改善量，且严格包率、有效交付率、QA、最差器件和恢复指标均不越过非劣阈值时才接受。
- 第 22 小时仍有 `STRICT_QUALITY_REQUIRED` 缺口时，冻结当前最佳卡并标记降级候选；最终 `pair_verdict` 必须等 22–23 小时包验证完成后判定。内部门禁超时是 SLO 失败，不自动使包无效。

## 5. 故障处理顺序

### MCP 超时或服务错误

先读取结构化错误与操作账本。确认未产生副作用且错误可重试时，才按剩余 deadline 退避；若服务端可能已执行但本地未记账，进入 `OUTCOME_UNKNOWN → RECONCILING`，按远端任务 ID/幂等键查询，禁止直接重复拟合。持续失败时保留当前最佳已验证卡并切换到另一器件或最终验证。

### 国产大模型限流或不可用

使用已验证的备用国产模型；若仍不可用，执行预定义的确定性降级策略，同时保留已发生的合规调用证据。结构化输出修正次数和模型切换次数受配置预算约束，禁止无限自愈。

### 拟合不收敛或 QA 退化

停止扩大参数搜索，回滚到最近已接受模型卡，缩小参数组或更换已登记策略。

### 进程中断

获取单一恢复所有权，校验状态/图/配置/契约版本并读取最近完整检查点；先对账未完成操作，再恢复最佳已验证卡和剩余预算，从下一未提交节点继续。最新检查点损坏时回退上一完整点；不重建已完成会话，除非官方接口明确要求。

### 时间不足

立即停止低收益 retune，执行最终 QA、Schema 校验、日志封存和包校验。若只能形成降级包，必须记录 `VALID_DEGRADED_PACKAGE` 及原因；缺少 `SUBMISSION_HARD` 门禁时记录 `INVALID_PACKAGE`，不得伪装完成。平台上传/回执由 `submission_status` 独立对账。

完整故障分类、恢复步骤和减载顺序见 [Agent 性能与恢复运行手册](../operations/agent-control-runbook.md)。

## 6. 提交前人工复核

- 两个器件和两个模型卡没有交叉。
- 文件可打开、可读取、命名符合官方要求。
- 运行日志从启动到冻结连续完整。
- 运行总结中的统计与日志一致。
- 操作账本没有未对账的副作用，重复副作用为 0。
- `pair_verdict` 明确为 `STRICT_COMPLETE` 或 `VALID_DEGRADED_PACKAGE`，`submission_status` 已在官方截止前 `CONFIRMED`；包结果与交付状态未混用。
- 没有 Token、API Key、临时缓存和测试原始数据。
- 上传完成后保留平台确认信息。
