# 契约与交付物规划

## 1. 契约优先

本项目不在取得官方材料前虚构 Schema。官方契约目录后续必须保存版本、来源和确认日期；项目内部运行控制 Schema 单独放在 `contracts/runtime_control`，必须明确标记为内部契约，不能冒充官方字段。

## 2. 契约目录

| 目录 | 计划内容 |
|---|---|
| `contracts/mcp` | MCP 工具清单、请求/响应、错误、会话和限流契约 |
| `contracts/model_card` | 官方 ASM-HEMT 模型卡 Schema 和校验要求 |
| `contracts/run_log` | MCP、LLM、决策、参数、QA 和时间统计日志契约 |
| `contracts/run_summary` | 单次竞赛运行总结格式 |
| `contracts/decision_record` | Agent 每次决策的结构化记录格式 |
| `contracts/runtime_control` | 内部 StageResult、OperationRecord、CheckpointManifest、CompletionVerdict、FailureRecord 和 PerformanceReport；不属于官方模型卡 Schema |

## 3. 正式交付物

测试日结束前必须形成：

- 器件 1 模型卡。
- 器件 2 模型卡。
- 器件 1 运行日志。
- 器件 2 运行日志。
- 一份全局运行总结。

测试日开始前必须具备：

- 完整代码仓库。
- Agent 图和状态定义。
- Agent 主入口。
- 依赖声明。
- 架构图。

当前骨架只覆盖上述内容的目录和设计位置，不生成正式文件模板。

## 4. 运行日志最小证据链

整条证据链需要能够回答以下问题。官方两份运行日志严格服从官方 Schema；无法或不允许写入官方日志的内部 span、操作账本、恢复和聚合字段进入 `quality/` 报告，只有官方允许扩展时才映射到提交文件。

1. 哪个器件、哪次运行、哪个 MCP 会话。
2. 在什么状态下调用了什么工具。
3. 调用目标、UTC 起止、同进程单调时钟计算的 duration、等待/执行耗时、结果和稳定错误分类是什么；不同进程的单调时钟值不互相比较。
4. 使用了哪个国产大模型，调用次数和 Token 统计是多少。
5. Agent 看到了哪些事实、有哪些允许动作、为何选择当前动作。
6. 参数卡从哪个版本变为哪个版本。
7. RMSE 代理和 QA 如何变化。
8. 为什么接受、retune、回滚或停止。
9. `span_id/operation_id` 的依赖关系是什么，运行后派生出的关键路径是什么，副作用是否已确认并关联哪个检查点。
10. 崩溃时从哪里恢复、如何对账未知结果、是否发生重复副作用。
11. 每个阶段的适用性、要求等级与结果是什么，最终为何判为严格包、降级有效包或无效包，平台交付状态是什么。

认证 Token、API Key 和其他密钥不得写入日志。

## 5. 冻结与校验

提交前校验与冻结顺序：

1. 分别完成两器件最终验证：模型卡符合官方 Schema、可由指定仿真链加载、器件映射正确，然后原子冻结两份卡。
2. 由冻结卡和不可变事件源组装 2 卡、2 官方日志、1 份只含官方 Schema 允许字段的官方总结及文件清单；此时包仍是待判定候选。
3. 官方日志/总结满足官方字段、命名和反作弊要求；每器件有效 MCP 调用、整组国产大模型真实决策证据达到确认口径。
4. 日志、总结、模型卡版本及摘要相互一致，无密钥、临时文件或正式测试原始数据泄露。
5. 内部质量报告确认操作账本无未对账的 `IN_FLIGHT/OUTCOME_UNKNOWN`，恢复/失败均可分类，关键路径和统计可重算。
6. 校验器基于完整包证据给出内部 `device_verdict` 与 `pair_verdict`；降级有效包不得冒充严格包，执行状态不得冒充结果。内部判定只有官方 Schema 明确允许时才映射进官方总结。
7. 再次执行包 Schema/数量/摘要校验并原子冻结包，不再覆盖。
8. 上传后单独更新 `submission_status`；回执未知时对账，官方截止前确认状态和平台摘要。

每次运行的内部质量报告放在 `artifacts/runs/<run_id>/quality/`，至少包含关键路径、阶段耗时、严格/降级包判定、提交状态、失败率、恢复记录和检查点开销；盲测聚合完成率只出现在内部报告，正式单次总结只能报告本次结果。内部报告是否属于官方提交包以官方契约为准。
